# FigImport PSD 文字转图片修复

修复版本：社区版 `2.1.0-preview.8`。日期：2026-10-14。

## 原因

用户提供的 PSD 中有 145 个原生文字图层，嵌入智能对象中还有 3 个文字对象，共 148 个可解析文字对象。没有发现竖排、弯曲或非等比变换导致的文字回退。

旧构建器要求字体族和字重同时匹配，只要整段或任一样式区间匹配失败，就用 PSD 保存的文字缓存图片代替整层文字。保存文字内容到节点数据并不等于创建可编辑文字。

文件的字体分布（不含智能对象内的文字）：

| PSD 字体名称 | 文字图层数量 |
| --- | ---: |
| NotoSansHans-Medium | 78 |
| NotoSansHans-Regular | 31 |
| NotoSansHans-Bold | 4 |
| DINPro-Medium | 21 |
| DINPro-Regular | 7 |
| AdobeHeitiStd-Regular | 3 |
| Alibaba-PuHuiTi-M | 1 |

本机注册的 Noto 中文字体采用 `Noto Sans SC` 名称，无法通过旧名称直接匹配；有些字体的注册名称把字重放在字体族内，例如 `Noto Sans SC Medium / Regular`。旧匹配逻辑不认识这种结构，也不能将阿里巴巴普惠体的 `M` 字重缩写识别为 `Medium`。字体注册表不能证明字体一定可被 Figma 加载，修复以插件运行时返回的可用字体及加载结果为准。[Figma 字体加载 API](https://developers.figma.com/docs/plugins/api/properties/figma-loadfontasync/)

## 修复行为

- 优先使用原字体，支持候选字体优先级、字体族内嵌字重和常见字重缩写。
- 普通 PSD 文字缺字体或加载失败时，使用可加载字体创建原生 TEXT；保留文字内容、字号、颜色、字距、行距及样式区间。
- Noto 旧名称优先尝试 Noto 简体中文字体；其余缺字体按文字内容选择可用字体。字体替代会在完成页明确提示，并在节点数据中记录源字体、实际字体和适用区间。
- 只有无可用字体、竖排/弯曲或不支持的文字变换等情况继续保留缓存外观。PDF/AI/EPS 在 preview.11 起使用默认字体保留可编辑文字。
- 维护社区版的匹配及构建逻辑；保留已有的 FigImport 插件 ID 和窗口标题。

字体替代保证保留编辑能力，不保证源字体的字形和排版完全一致。字体加载失败会尝试其他可用字体，不再直接中断整个导入。

## 验证

使用同一 PSD 和固定模拟 Figma 字体列表对照旧构建器与修复构建器：

| 检查项 | 旧构建器 | 修复后 |
| --- | ---: | ---: |
| 原生可编辑文字 | 7 | 148 |
| 文字缓存图片回退 | 141 | 0 |
| 使用替代字体的文字对象 | 0 | 120 |

最终 `code.js` + `ui.html` 的本地浏览器导入也得到 148 个 TEXT、0 个文字图片回退、5 个画板；完成页提示“部分文字使用替代字体，请核对字形与排版”。原图像、智能对象图像和蒙版图像仍正常保留，共 95 个图片节点。

社区版类型检查及核心回归通过；新增 10 项文字回归通过；社区预检/提示、发布体积、内嵌资源完整性、启动错误和界面回归通过。源码与打包回归使用严格节点测试环境，不是 Figma 渲染器。真实 Figma 的字形、坐标及效果还需视觉核对；该样本另有 8 个内外发光效果兼容问题，未将其算作文字修复成功。

原 PSD SHA-256：`41bcb55f0ec79ae5c1966aa9af49f1c862d3b141f9fa7d4d9431a5ccce5607cc`。分析与测试在本地进行，源 PSD 未改写。

## 使用修复构建

在 Figma 的开发插件入口导入 `community/manifest.json`，运行 FigImport，再导入原 PSD。也可以解压 `community/dist/figma-import-community-2.1.0-preview.8-plugin.zip` 后导入其中的清单。

社区已经上线的版本不会因本地源码修改而自动更新；需要使用社区目录的构建重新发布到已有条目。本次没有重新发布社区插件。替代字体对象导入后请核对字形与排版。
